Persist a restoration-started/version binding in durable operation state before writes, require its receipt on every subsequent attempt, and reserve absence-compatible behavior for explicitly identifiable legacy/not-yet-started states. Add this two-file-loss case for both restoration callers. This is a static control-flow finding, not a claimed executed reproduction.

2. **P2 — Rebase onto expansion fails after publishing operation metadata and ORIG_HEAD.** `src/git/workflow/rebase/publication.cr:104`–105, called after `src/git/workflow/rebase/initiate.cr:51`–55. The rescue clears `rebase-merge`, but it does not restore the previous ORIG_HEAD, and a callback can already observe the metadata. This violates expansion-before-metadata/publication for the onto movement. Prepare and bound the move's converted writes before writing initial operation state or ORIG_HEAD, then publish the prepared plan with the existing state/index guards. Add an onto expansion regression preserving a preexisting ORIG_HEAD and asserting no operation metadata is visible before rejection. The ordering is directly visible; no runtime reproduction was needed.

The condition bounds each map independently, so a predecessor with `max_entries` records plus a target with `max_entries` records serializes `2 * max_entries` records. Enforce the documented aggregate record/path count with overflow-safe arithmetic before constructing fields, and add a case where both individual maps fit but their combined count exceeds the allowance.
